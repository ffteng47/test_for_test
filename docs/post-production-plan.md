## 0. 现状判定（工序对照）

| 工序 | 行业做法 | 我们现状 | 判定 |

**一句话结论：报价里唯一压不动的成本是 prooflisten，而它现在连量具都没有。**

## M1 机检闸门：把「报告里有数」变成「不合格不让交」

| | |
|---|---|
| 目标 | 导出后机器判定，不靠人读数字；不达标在**前端**红着 |
| 改动 | `backend/master_audio.py`：新增 `inspect(path)` 出全项实测（LUFS / RMS_level / 真峰值 / 时长 / 章节数 / 体积 / 首尾静默），`build_report` 改为消费它；判据拆两层——`gate()` 客户口径（只有响度和真峰值能拦交付）、`channel_gate()` 渠道口径（RMS / 峰值 / 体积，只报数不拦），阈值仍然全部在模块顶部。`_normalize_master` 把 `通过` 写进 `projects/<slug>/delivery_report.json`；`GET /api/delivery_report` 读它；前端 `/export` 在 `通过=false` 时成品行红字 + 禁下载 |
| 验收 | `master_audio.py --check` 每项出「实测值 + PASS/FAIL」；`--inspect 成品` 只判定不改写、不合格非 0 退出；自检里带一个**削顶反例**，必须两项全 FAIL（闸门放行坏样本比阈值偏严危害大） |
| 工作量 | 1 人日（纯 CPU，**不需要 GPU，不需要产新音频**） |
| 依赖 | 无。后端改动走安装器 + 重启（`usage-wiki.md` §4.2/§4.3） |

### M1 实测结果（2026-10-11，已部署并在真导出链路跑通）

**闸门反例踩到一个仪器坑，值得记下来**：ffmpeg `lavfi` 的 `sine` 源**不是满幅**，实测峰 −18.06 dBFS。第一版反例拿它当「顶满的样本」，量出 −22 LUFS，是个偏轻信号——闸门确实 FAIL 了，但 FAIL 的原因是响度过轻，反例并没有证明它能拦削顶。加成 `volume=24dB` 才是真削顶（0 dBFS / +0.04 dBTP），断言随之从「不是全 PASS」收紧成「没有一项 PASS」。

现有母带 `projects/shuxue/audiobook.m4b` 全项实测（`--inspect`，退出码 0）：

| LUFS | 真峰值 | RMS | 时长 | 章节 | 体积 | 头静默 | 尾静默 |
|---|---|---|---|---|---|---|---|
| −16.06 | −2.19 dBTP | −16.33 dB | 1399.78 s | 259 | 20.4 MB | 16 ms | 0 ms |

客户口径 **2/2 通过**；渠道口径 2 项 FAIL（RMS 差 1.7 dB、峰值差 0.8 dB）——与 `channel-master-checklist.md` §2.2 的结论一致，属 M4 的 profile 问题，不该在这里拦客户收货。

接线决定与踩过的坑：

- **测闸门的方式本身有陷阱**：`/api/delivery_report` 是**沿当前软链**反查书目录的，所以手动把 `delivery_report.json` 的 `通过` 改成 false 来验前端拦截，改的就是**当前那本活书**的真实交付状态——它当场真的禁掉了下载。测完必须还原成 `--inspect` 重跑出来的那份，不能留手改的数。
- **闸门只拦「文件离开」，不拦「听见」**：前端的 `下载` 在 `通过=false` 时禁用，`播放` 不禁（试听是内部复核手段，拦了就没法查为什么不合格）。对客户交付而言以下载为准。
- 数量级上「未机检」与「不合格」在界面合并显示为红色——因为两者都不该出货；但文案分开写，`未机检` 那句是「还没走过母带后期，成品按不合格对待」，避免把「这本没导出过」误读成「这本坏了」。
- **归一崩了也必须写一份 `通过=false` 的报告**。否则前端读不到文件只能显示「未机检」，界面分不清「这本没导出过」和「刚崩了、成品不合格」——后者是最需要拦住的。
- 报告经 `GET /api/delivery_report` 出来，路径从 `audiobook.m4b` **软链反查** `projects/<slug>/`，不直接读 `root_dir`（那里是多本书共用的软链根，见 M1 之前的 `fix_master_report_dir.py`）。
- **判定必须落在真成品上**，于是导出末尾多一道 `finalize()`。这是重跑一次导出才暴露的：归一只看得到中间 WAV，报告里 `章节数: 0→0`、体积 117.7 MB（成品 m4b 实际 20.4 MB），**「章节标记没丢」这条判据从来没生效过**——而「导出把 259 章弄没了」恰恰是这一层唯一拦得住的东西（本轮就真踩过两次，见 §M4 前置）。附带好处：AAC 编码对响度的影响也被算进判定（WAV −2.48 dBTP → m4b −2.19 dBTP，差 0.29 dB，仍在窗内）。代价是每次导出多跑两遍全量解码（≈ +40 s）。

## M2 拼接痕机检（重新定义「底噪检测」这一缺项）

| | |
|---|---|
| 为什么 | 渠道要的是「静默段够干净」。我们的静默是数字零，`silencedetect` 测出来必然满分——**这项对我们真正该测的是段边界有没有爆音**：TTS 段尾常留半个波形/直流偏移，`+=` 硬接进数字零就是一记 click |
| 改动 | `backend/master_audio.py` 加 `boundary_flags(audio_dir_or_timeline)`：每个边界取前后 ±5 ms 的一阶差分最大值，与该段内部中位差分比，超倍数阈值的段号 + 时间点落 `boundary_flags.json` |
| 验收 | 拿**已生成的 259 段**跑一遍（不需要 GPU）；人工复听被 flag 的前 10 条，命中 ≥ 6 条才算阈值可用；然后**反向确认误报率**——flag 数应远小于总段数 |
| 工作量 | 0.5–1 人日 + 1 h 人工复听标定 |
| 依赖 | 无。**阈值必须先标定再写进闸门**，否则 M1 会被误报淹没 |
| 后续（不在本轮） | flag 出来的段号在「剧本工作台」按列表一键 `↻ 重生成` —— 这才是 AI 产线里「剪辑」的等价动作（剪＝重生成一条） |

### M2 实测结论（2026-10-11，现有 372 段全量，纯 CPU，不需要 GPU）

`boundary_flags` 一落地就跑完了全量：**flag 数 0 / 372**，最大跳变 −34.34 dB（阈 −12 dB），中位 −78 dB。**「段尾硬边接零会爆音」这个假设被证伪**——本产线的段边界不产生 click。

但同一台仪器量出了真问题，方向和假设不同：

| 量 | 分布 |
|---|---|
| 段首静默 | 最小 37 / **中位 437** / p90 770 / 最大 1273 ms |
| 段尾静默 | 最小 0 / **中位 90** / p90 155 / 最大 208 ms |

段间标称静音 500 ms（同人 250 ms）是**固定值**，可两头拖的静默是 TTS 自己给的**随机值**，所以**实际停顿 ≈ 90 + 500 + 437 ≈ 1.0 s，抖动 ±850 ms**。这才是真人后期「剪掉多余气口」那格在我们这里的等价物——不是剪爆音，是**剪段首死气**。→ 见 M2b。

## M2b 段首静默归一（M2 实测派生，取代原「爆音」假设）

| | |
|---|---|
| 改动 | `app/tts.py` 的 `combine_audio_with_pauses` 与 `compute_timeline` 共用一个「段首裁到只剩 ~80 ms」的前置步骤（pydub 自带 `detect_leading_silence`，不加依赖）。**两处必须同时改**：只改拼接不改时间轴，章节标记就会整本漂 |
| 为什么归在导出层 | 它发生在合并时，纯 CPU，**不需要重跑任何音频**；改安装器 → 重启 → 重新导出即生效 |
| 验收 | 重跑 `boundary_flags`：段首静默中位落到 80 ± 20 ms、最大 ≤ 200 ms；`delivery_report.json` 的时长漂移 = 预期缩短量（≈ 0.36 s × 段数），不是随机数；259 章时间轴对得上原文 |
| 副作用（必须先记账） | 成片会变短（372 段 ≈ 短 2 分钟），`cost-model.md` 的 252.5 字/分钟与报价换算要跟着更新 |
| 工作量 | 0.5 人日 + 一次重导出 |
| 依赖 | M2 的仪器（已完成）。**M1 的「首尾静默」判据等它做完才有意义** |

### M2b 实测结果（2026-10-11，已部署并跑通）

安装器 `deploy/patches/add_leading_silence_trim.py`（幂等，备份 `tts.py.bak_pre_lead_trim`），裁剪常量在 `app/tts.py` 顶部：`LEAD_SILENCE_FLOOR_DB = −45.0` / `LEAD_SILENCE_KEEP_MS = 80`（**设 None 即关闭**）。先在 372 段上离线干跑，再重启服务真跑两条导出路：

| 量 | 裁剪前 | 裁剪后 |
|---|---|---|
| 段首静默 | 中位 437 / p90 770 / 最大 1273 ms | **中位 76 / 最大 88 ms** |
| 段首跳变 dB | 最大 −65.54 | 最大 **−40.38**（阈 −12，超阈 **0 段**）→ 没切进语音 |
| 成片时长（同一本书重导） | 1508.62 s | **1399.75 s（−108.9 s，−7.2%）** |
| 验收 | −16.0 LUFS / −2.48 dBTP / 通过 | −16.0 LUFS / −2.2 dBFS / 通过，**259 章、末章 END 正好落在文件尾**（章节轴没漂，MP3 与 M4B 时长一致） |

干跑时踩到一个量纲坑，值得留在文档里：pydub 的 `detect_leading_silence` 阈值是**绝对 dBFS**，`master_audio.head_tail_jump_db` 的静默起点是**相对本段峰值**（`−45 dB + peak`）。段峰约 −10 dBFS 时两者差 10 dB，所以裁剪后残留的 80 ms 会按后者读成「静默 0 ms」。**两个数不能直接对照**，判「有没有切进语音」只看跳变那一项。

## M3 prooflisten 工位（本轮最重要的一格）

| | |
|---|---|
| 为什么 | `price-list.md` 的错读率阈值是 `[待定] ‰`、`cost-model.md` §5 的头一项「听感返工率」是假设值。**这两个数决定毛利率上限**，不做出错检出的工位就永远定不下来，报价永远是在赌 |
| 改动 | 前端「剧本工作台」加**审听模式**：逐段连播 + 四个键（✓对 / ✗错读 / ♪音色不对 / ↻需重生成），落 `chunks.json` 该段的 `listen` 字段（`{result, note, at}`，chunk dict 加键不动 schema）；导出前检查条显示未审段数 |
| 验收 | 全听一本 5 万字（成片 ≈20 min）能产出三个数：① 错读段数/总段数 = 出错率 ‰ ② 人工耗时 / 成片时长 = prooflisten 工时比 ③ 需重生成比例 = 返工率。三个数回填 `cost-model.md` §5 与 `price-list.md` |
| 工作量 | 2 人日（前端为主，免重启）+ 全听一本人工 1–2 h |
| 依赖 | 无技术依赖；**需要一本已生成的书**（现成的 259 段就够，不用新产） |
| 判据风险 | 合成语音不会累，但错读**没有「重录一条」的自然修复**，且集中在生僻字/数字串/多音字——统计口径要按这三类分开记，否则一个平均数会把问题藏起来 |

### M3 机检口径基线（2026-10-11，`/api/qc` 实测；**不是**听感返工率）

审听工位还没上，但 ASR 回听一直在记（`noveldb.segments.qc_err`）。先把这一半的数落下来，人工那一半才有个对照。

现有这本书（`projects/shuxue`，259 段 / 6126 字）：

| 段数 | pass / retry / unchecked | 零错读段 | CER>2% | CER>5% | CER>8% | 字数加权 CER |
|---|---|---|---|---|---|---|
| 259 | 253 / 6 / 0 | 91.5% | 14 | 8 | 6 | **1.25%** |

retry 段的分布很说明问题：`[(17, 46.7%, 25字), (120, 14.3%, 23字), (127, 20.0%, 21字), (155, 100%, 43字), (183, 35.7%, 13字), (188, 14.3%, 18字)]`。中位 CER 是 0.0000，p90 也是 0.0000——**九成的段是干净的，问题全集中在极个别的短段上**，而 1.25% 这个加权平均里有 43 字那段（CER 100%，即整段没对上）一个就占了三分之一。所以「出错率 1.25%」这句话是骗人的：一个平均数正是 §判据风险 说的那种把问题藏起来的数。

**机检口径 = 6/259 = 2.3% 段需重生成**（阈值 `backend/asr_qc.py` 的 `ERR_THRESHOLD = 0.08`）。但这个数**不能直接当报价里的听感返工率**，两个方向都偏：

- **偏高**：ASR 自己就不认识数学名词和数字串，它听错也算错读。
- **偏低（这才是要命的一侧）**：ASR 只对文本，**听不出音色漂移、语气错、多音字念成另一个合法读音**——字面全对而听着是错的，机检恒过。而 `type: design` 逐句重抽造成的音色漂移恰好属于这一类。

结论：机检的 2.3% 是返工率的**下界都不一定成立的一部分**，人工那一遍量的是机检覆盖不到的类。审听工位要记的四类里，`✓对 / ✗错读` 与机检重叠，`♪音色不对 / ↻需重生成` 是机检完全空白的那格——**这两个类的占比就是报价里唯一还没有的数**。

### 工位已上线（2026-10-11，复验通过）

`deploy/patches/add_prooflisten.py` → `POST/GET /api/prooflisten`；导出前检查条多一行「人工审听 x/259 · 未审 n · 错读/音色/需重生成 · 工时 min」；判定落 `projects/<slug>/prooflisten.jsonl`（重听同一段以最后一条为准，工时照计）。

**判定键在底部播放条，不在剧本工作台右侧。** 第一版把「◎ 审听 + 四类判定」放在 `ScriptView` 的 280px 右栏（`position: sticky`），实测不可用：右栏比视口高，判定块落在折叠线以下，一展开就把「质检」块顶出可视区（用户原话「根本看不到四个判定键，并且遮挡住了质检窗口」）；而听的时候眼睛和手都在底部那条播放条上（▶ / 重生成本句）。所以现在：

| 位置 | 内容 |
|---|---|
| 底部播放条右侧 | `◎ 审听` 开关（开 → `◉ 审听中`） |
| 开审听后，播放条中段（波形让位） | `1 ✓对` `2 ✗错读` `3 ♪音色不对` `4 ↻需重生成` + `已审/总段` + 一行快捷键提示 |
| 剧本工作台 | 只留进度条 `◎ 审听 x/y · 未审 n` 和每段的判定角标，不再有判定按钮 |

快捷键（只在审听模式生效，输入框里不抢键）：`空格` 重听本段、`1/2/3/4` 判定并按下后自动连播下一段**有音频的**、`n`/`b` 下/上一段、`Esc` 退出。审听状态刻意留在 `TransportBar` 组件里（它全生命周期只挂载一次，判定键也只在这里）。母带导出 LIBRARY 的「播放」同步改成播放中显示 `■ 停止`（单例播放器，整书 25 min，不能只能一直播）。

**踩到并修掉的坑：书目录不能靠 `realpath(CHUNKS_PATH)` 反查。** `chunks.json` 虽然写在 `domain.SWAP_ENTRIES` 里，实测服务器上它是 `alexandria/` 根目录的**真文件**（根 75029 B ≠ `projects/shuxue/chunks.json` 65216 B），反查就退到多本书共用的软链根，判定会串书。唯一入口改成 `projects.json` 的 `active`（复用 `domain.PROJECTS_DIR` + `registry()`，不自己拼路径）。**成品和 `delivery_report.json` 仍是软链反查——只有 `chunks.json` 这一条不能信。**

**上线时把整个界面打死过一次**：给审听统计起的 computed `listen` 撞上 `ScriptView` 原有的方法 `listen()`（试听本句）。Vue 2 里同名不报错，运行时才 `Invalid handler for event "click": got undefined`，组件树渲染中断 → hash 路由下所有 `router-link` 的点击监听一起失效 → 症状是「左侧导航全点不动」。`vite build` 与模板编译都过，**只有跑起来才看得见**；因此补了一条固定验收动作：无头 Chrome 逐路由 `--dump-dom --enable-logging=stderr`，控制台有 `[Vue warn]` 就不许上线（做法记在 `usage-wiki.md` §7）。回滚不用重传文件——`studio/assets/` 只增不减，改 `index.html` 的 hash 指回上一版就行。

**第二个坑：模板引用了 `data()` 里没有的键，路由级验收抓不到它。** 把判定键搬进播放条时漏注册 `VERDICT` → `Cannot read properties of undefined (reading 'ok')`，`TransportBar` 渲染中断，症状是「点了审听，状态变了，界面纹丝不动」。逐路由 `--dump-dom` **全绿**，因为这块 DOM 只在点击之后才存在。验收口径补一条：**只在交互后出现的块，必须带交互验**（用用户开着的 CDP 端口 `9222` 直接驱动页面：点开关 → 数 `.transport .vd` 是否 4 个 → 派发 `keydown` 验 `n/b/空格/Esc`）。

**第三个坑：`reactive()` 之后才挂上去的键不被追踪，computed 永远缓存初值。** `store.js` 原本是 `reactive(structuredClone(mockStore))`，然后才 `store.mode = 'mock'`、`busy`、`toast`、`projects`、`engines` —— 而 `mock.js` 里根本没有 `mode` 这个键。后果：`TransportBar` 的 `live()` 卡在 `false`，而 `store.mode` 实测已经是 `'live'`，于是 `onPlay()` 每次都走「演示模式」分支只翻一个假图标，**播放按钮点了毫无反应**（模板里内联写 `store.mode === 'live'` 的地方看着是对的，因为渲染函数每次重新取值，只有 computed 被缓存——这正是最难看出来的一半）。`system.qc/delivery/listen` 同理；段上的 `listen` 也一样，`loadChunks()` 的段对象字面量里没有 `listen` 键，判定后高亮不动。修法：**所有键在进 `reactive()` 之前就在对象里**（`reactive(Object.assign(structuredClone(mockStore), { mode, busy, toast, projects, engines }))`，mock 的 `system` 补 `qc/delivery/listen: null`，段字面量补 `listen: null`）。CDP 复验：`vm.live === true`，点 `▶` 后 `store.transport.url` 落到本段 `/voicelines/*.mp3`。audible 起声在这台机器上仍验不了 —— 后台标签页 `navigator.userActivation.hasBeenActive === false`，连 CDP 派发的 `Input.dispatchMouseEvent` 都不算用户激活，`audio.play()` 一律 `NotAllowedError`（连新建的 `new Audio()` 静音播也一样被挡，所以这是驱动假象，不是按钮坏了）。

**`✓ 确认锁定` 已删除（不是坏在第二个坑里，是它本来就没作用）。** `confirmSeg()` 只写 `seg.confirmed = true`，后端没有任何端点，`loadChunks()` 每 15 s 把 `confirmed` 重算成 `c.status === 'done'` —— 按钮按下去下一轮就被覆盖，且 `status==='done'` 的段本来就是 `true`，等于零效果。人工这道闸门现在由审听判定承担（落 `prooflisten.jsonl`，跨重启留存），所以顺手删掉 `confirmed` 这个死字段和 `ScriptView` 的「x 已锁定」计数，段前的绿勾改由 `s.status === 'done'` 驱动。


**CDP 还有一个假象**：后台标签页 rAF 冻结 → `mode="out-in"` 的过场永远停在 `fade-leave-active`，看着像「切换路由后白屏」，其实标签页一亮就好。

还差的那一步不是代码：**人工全听 259 段**（成片 ≈20 min，预计 1–2 h）。工时按「进入该段 → 按下判定键」的墙钟累加，重听同一段以最后一条为准、工时照计。
