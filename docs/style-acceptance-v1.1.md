## 1. R7 期待管理：证据按功能分档，类型由引擎预定

**每章必须由剧情引擎预先指定 `expectation_function`，只取 `establish` / `escalate` / `payoff` 之一。
评分器不得读完正文后再自由选择对自己最有利的类型。** 这条顺序是全部可信度的来源：类型先定，证据后验。

| function | 必须提供的证据 | 通过条件 |
|---|---|---|
| `establish` | 引用正文中的新信息缺口、异常或未解释行为 | 能明确指出读者**新产生了什么问题** |
| `escalate` | 引用升级动作，并关联既有期待或伏笔 ID | 能说明原有期待为何变得更紧迫 / 更危险 / 更重要 |
| `payoff` | 引用兑现正文，关联原始伏笔 ID、设置章节与预期兑现条件 | 兑现内容与原始伏笔有**可核验的对应关系** |

输出结构（字段规格，示例中的伏笔是虚构的，不代表任何一章已通过验证）：

```json
{
  "dimension": "expectation_management",
  "function": "payoff",
  "score": 4,
  "evidence": {
    "quote": "正文中的兑现原句",
    "foreshadowing_id": "FS-012",
    "setup_chapter": 3,
    "payoff_chapter": 8,
    "expected_payoff": "此前发现的印记能够识别密室入口",
    "actual_payoff": "印记与密室入口产生对应"
  },
  "verdict": "pass",
  "confidence": 0.92
}
```

**强制校验（三项，任一不满足 ⇒ 不得仅凭模型解释认定为有效兑现）：**

1. `quote` 必须能在正文中**逐字定位**（子串命中，不是语义相近）。
2. `foreshadowing_id` 必须存在于**冻结的伏笔账**（该章提交时刻的 State 快照，不是之后的版本）。
3. `payoff` 必须满足伏笔账里**预先记录的兑现条件**；兑现条件在设置伏笔时写入，事后不可改写。

**现状（决定这条要花多少工程量）：**

- 伏笔账只是 `StoryState.foreshadowing: List[str]`（`plot_engine/models/state.py:64`）——
  **无 ID 形态、无兑现条件字段、无状态机**；协议侧同样只列了类型名
  （`alexandria-spec-v0.2/01_event_protocol.md:99-103`），§4.1 的 payload 规范**没给这两个类型定任何键**。
- `FORESHADOWING_SET / FORESHADOWING_PAID` 在 reducer 分派表里指向**显式 no-op**
  （`plot_engine/reducer.py:46-47` → `plot_engine/reducers/plot.py:14-17`，注释自认「Phase 0 剧情层事件只做哈希重打」）。
- LLM 抽取通道**显式拒收**这两个类型（不在 `PAYLOAD_SCHEMA`：`plot_engine/llm_extract.py:32-47`，
  拒收点 `:163-164`）⇒ 就算正文写了伏笔，抽取也不会产出它。
- 引文定位：`source_ref` 实际是 `para:N` 这类**调试定位符**（`llm_extract.py:193-195`），
  全仓库**没有任何一处**校验引文与正文一致（`validator.py` 不引用 `source_ref`）。
- ⚠️ 因此 `docs/alexandria-position-and-phase1-prose-layer.md:30` 的「伏笔可追踪、必兑现 ✅」
  **与代码事实不符**，见 §7 勘误。

**落点（按依赖顺序）：** 伏笔账结构化（`Foreshadowing{fs_id, setup_chapter, expected_payoff,
status}`，改 State ⇒ 走 schema_version 与快照兼容）→ reducer 真实写入 → 抽取通道承接 `FORESHADOWING_*`
（附 payload 规范，同时改 `01 §4.1`）→ `expectation_function` 进 ChapterContract（derive 期定，不由评分器选）
→ 三项强制校验进 validator（引文逐字命中是最先能落的一条，它只依赖正文，不依赖伏笔账改造）。

## 2. 剧情引擎：每章必须有非空状态差异（这是引擎的责任，不是文笔层的）

条款原文照纳，逐条给落点：

- 每章必须声明**至少一个**预期状态变化。
- 变化必须绑定：具体对象、变化前状态、变化后状态、触发事件。
- **过场章也必须产生有效变化**（某人获得新信息 / 关系变化 / 风险增加 / 角色作出承诺）。
- 不许用「气氛更紧张了」「人物更成熟了」这类**无法验证的描述**充当唯一状态差异。
- 两处闸：规划期没有有效变化 ⇒ **不得进入正文生成**；正文写完预期变化没发生 ⇒ **提交不得通过**。

```json
{
  "chapter": 8,
  "expected_state_diff": [
    {"entity": "character_03", "field": "known_facts",
     "before": ["FACT-021"], "after": ["FACT-021", "FACT-034"],
     "trigger_event": "EVENT-088", "evidence_required": true}
  ]
}
```

**两层职责，互不替代（这条是本文的结构核心）：**

| 层 | 判什么 | 判据形态 | 失败后果 |
|---|---|---|---|
| **剧情引擎** | 状态变化**是否有效、是否发生** | 硬规则（H 级），确定性比对 | 规划期拒绝开工；提交期拒绝入账 |
| **文笔评分器** | 正文**是否让读者理解了**这项变化 | rubric 条款 + 证据引用 | 判不过 ⇒ 进修订环重写该场 |

职责分开的收益写死了两个失败模式：**水章蒙过评分器**（引擎先拒绝空差异）和
**评分器越权裁定剧情成立与否**（它只能判「说不说得清」，不能判「该不该发生」）。

**现状与两处必须先裁定的冲突：**

1. 我们的 `must_change` 已经是同一族概念：`CharacterChange{character_id, field, operation,
   target, expected_value}`（`plot_engine/models/contract.py:46-58`，协议镜像
   `04_contract_protocol.md:101-113`）。缺 `before/after` 对偶与 `trigger_event`。
   ⇒ **补齐这些字段是协议变更**（改的是 04 的冻结文本），不是实现靠拢。按 I2 的线：代码向文本靠拢 = 实现义务；
   **改文本 = 定尺权在你**。本文把它列为待裁定第 ①。
   可先走的**不变更协议**的等价路线：用 `operation=add` + `target` + `expected_value` 表达增量，
   `before` 由提交前 State 快照重读，`trigger_event` 由 `required_events` 的 event_id 回推——
   这样 §2 的四要素在**现有 schema 内**就凑得齐。我推荐先走这条，等真需要 `before` 全量对偶时再改协议。
2. **空 `must_change` 目前是合法的**：`plot_engine/tests/fixtures/experiment_10ch.py:95` 明文写着
   「本章不推进：合法形态」，`derive.py` 里只有 Δ 实现性守卫（`:174-179`，每条 must_change 必须有能实现它的事件类型，
   否则 `ArcConflict`），**没有「非空下限」**。
   ⇒ 加下限会**直接改动尺的输入面**（原来允许不推进的章从此必须推进），因此它进尺必须先重跑基线；
   这条与 T2 的「#9 空契约下限规则」相邻但不同：#9 管的是**整张契约空**，本条管的是**状态差异空**。
3. `evidence_required: true` 这一位在现有结构里已有对应（`required_events` + H5.3 的兑现校验），
   不需要新造字段。

## 3. 人工盲评：冻结抽样与仲裁协议

- 首轮抽 **≥30 章**，其中**失败类 ≥15 章**（失败类指判死 / `NEEDS_HUMAN` / rubric 不过的章）。
- 这是**分层超额抽样** ⇒ 整体一致率必须**同时报两个数**：原始样本结果，与按真实生产分布加权后的估计。
  **不许把超采样本的比例当成生产总体的比例。**
- 流程：
  1. 自动评分完成后**冻结全部输出**，隐藏模型评分与模型身份。
  2. 人工评审 A 独立评分；人工评审 B 只对分歧样本独立复评。两人都不得查看自动结论。
  3. A、B 不一致 ⇒ 由**未参与初评的第三位**仲裁者审查原文、证据与冻结规则。
  4. 记录最终裁定、原始分数、分歧方向、原因类别、是否需要修改规则。

分歧方向必须分开统计（四象限）：

| 自动评分 | 人工最终裁定 | 名称 | 风险 |
|---|---|---|---|
| 失败 | 通过 | 假阳性 | 误拦好章节、过度重写 |
| 通过 | 失败 | **假阴性** | **坏章节漏过，直接影响内容质量** |
| 失败 | 失败 | 正确拦截 | 规则有效 |
| 通过 | 通过 | 正确放行 | 正常生产 |

**假阴性是重点风险指标。** 首轮还必须输出：各维度分数分布直方图、规则拦截量，
以及「1 分否决规则是否真的触发过」——**只在文档里存在而从未触发的规则视为无效规则**（§0 已声明它目前不可触发）。

**现状**：仓库里**没有**盲评、没有 A/B 双评、没有第三仲裁、没有一致率/分歧统计。
唯一的人工协议是「防线 2 · 机械服从人工抽检」（`docs/phase0-v3-three-arm-results.md` §4）：
**单人**、每臂分层 3 章、判据是「≥2 成文」。
⇒ **人力前提是硬约束**：现阶段只有 tff 一个读者。降级方案（必须明写是降级）：同一读者**隔时两读**
（A 读后 ≥24 小时再盲读第二批），第三仲裁人暂时空缺，所有 A/B 不一致样本进「待仲裁」队列而非当场裁定。
这条降级不影响四象限统计，影响的是「一致率」的可信度声明——报告里要按这个口径写。

## 4. R7 首轮不直接判死刑：观察模式

同意并落地为四条：

- 记录三次评分的**极差**、**证据缺失率**、**人工分歧率**。
- 先检查 `establish / escalate / payoff` 的**证据规格是否完整**（能不能填满 §1 的字段），再谈分数。
- 分歧主要源于**证据定义不清** ⇒ 先修规则、重新验证，不动维度。
- 只有「证据规格充分 + 人工参照明确」之后仍无法稳定评分，才把该维度标记为**不可靠**。

观察模式 ≠ 省略：R7 仍必须产出分数与证据，只是**不因为首轮分歧就永久否定这个维度**，
也不因为首轮分数就自动触发重写（自动重写的启用条件在 §6 定标之后另裁）。

## 7. 勘误（随本文一并生效）

**与代码不符**：伏笔账是无人写入的裸字符串列表，两个伏笔事件类型的 reducer 是显式 no-op，
