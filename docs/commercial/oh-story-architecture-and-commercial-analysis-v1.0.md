## 1. 项目定位与形态

**Oh Story 不是独立产品，而是 Agent Skill 包**——13 个 Skill + 7 个专用 Agent + 8 个自动化 Hook，部署进用户已在用的宿主 CLI（Claude Code / Codex CLI / OpenCode / ZCode / OpenClaw / Reasonix，外加通用 skills 路径）。

| 维度 | 设计选择 | 商业含义 |
|------|----------|----------|
| 形态 | Skill 包，按需调用 | 零安装摩擦，蹭宿主分发 |
| 算力 | 宿主模型 + 本地脚本（Node.js hook） | 零额外 GPU，成本 = API 费 |
| 记忆 | 文件系统（设定/大纲/正文/追踪独立文件） | 100+ 章长篇不丢伏笔，可 git 管理 |
| 控制 | 确定性门禁 + Hook + Agent 分工 | 防"没细纲就写正文""AI 味失控" |
| 平台 | 起点/番茄/晋江/七猫 + 知乎盐言/番茄短篇 | 直接对齐付费阅读节奏 |

核心口号：**"套路 = 确定性的情绪满足"**。方法论三步走：扫榜 → 拆文 → 商业化写作；四条主线：爆款逆向、剧情模块化重组、上下文状态分层管理、人机协同。

## 2. 架构分层详解

### 2.1 部署层：`story-setup`

- 把 skills、agents、rules、hooks 部署进写作项目（`.claude/agents/` 或 `.codex/agents/`），已有配置**安全合并**，不依赖全局目录。
- **`agents_version` 一致性机制**（当前 25）：版本不匹配 → 提示但照常并行；agent 文件缺失 → 降级 solo 模式。重部署后需新开会话。
- 多端部署有环境探测（曾修复 Reasonix/generic 误判为 OpenClaw 的 bug）。

### 2.2 路由层：`story`

- 模糊意图分发 + 自然语言触发映射（"帮我开书"→`story-long-write`，"这篇太 AI 了"→`story-deslop`，"沈栀现在什么状态"→自动查角色状态）。
- **作者记忆目录**：写作习惯以三态管理（原话证据 / 待确认 / 冲突替代），跨会话延续。
- 本地 Dashboard 浏览拆文库与项目文件树，内容不上传。
- **上下文预算工程**（其迭代重点，值得我方注意）：
  - `story-long-write` 的 SKILL.md 从 82KB 砍到 54KB；
  - 开书三阶段抽成按需读取的 `workflow-setup.md`——日更不再为用不上的建纲步骤付费；
  - 每次会话固定加载文本再降两成（开书 −30%、回炉 −41%）。

### 2.3 市场输入层：扫榜 ×2 + `browser-cdp`

- `story-long-scan`：起点/番茄/晋江/七猫榜单（新书榜、人气榜、书库新书）；`story-short-scan`：知乎盐言/番茄短篇风口。
- `browser-cdp`：CDP 协议复用浏览器登录态抓数据。
- 产出选题决策三段式：可行性、差异化定位、失败风险。
- 方法论本质（社区实测总结）："找跑通的骨架，换自己的肉"——灾难开局+翻盘机会+金手指+收小弟打脸反派，骨架复用、填充差异化。

### 2.4 逆向资产层：拆文 ×2

- `story-long-analyze`：黄金三章、爽点密度、节奏、五维评分；`story-short-analyze`：故事核、情绪曲线、反转设计、写作手法、共鸣分析。
- `chapter-extractor` agent 并行拆文。
- 产出 `拆文库/{书名}/`：角色、剧情、设定、章节、节奏.md、情绪模块.md；**每个情节节点锚定原文位置，标注情绪类型与强度**，提炼可复用技法。
- 写作 skill 通过 `对标/{书名}/` 引用这些资产——拆文不是一次性报告，是可消费资产。

### 2.5 生产层：写作 ×2 + 7 个 Agent 分工

**模型分层控成本**（社区核实版）：

| Agent | 模型档 | 职责 |
|-------|--------|------|
| story-architect | Opus | 顶层架构：题材、大纲、钩子、反转（深度思考活） |
| character-designer | Sonnet | 角色设计 |
| narrative-writer | Sonnet | 正文写作 |
| consistency-checker | Haiku | 快速事实冲突扫描 |
| story-researcher | — | 查资料 |
| story-explorer | — | 加载上下文 |
| chapter-extractor | — | 并行拆文 |

**长篇流程**（`story-long-write`）：开书（设定+卷纲+人物+前三章规划，**默认停在正文前**让作者确认）→ 每章先补细纲（目标情绪/情节点/闭环状态）→ narrative-writer 分批写正文 → consistency-checker 查事实与伏笔 → 去味审查 → `storyctl chapter commit` 写状态 → 重渲染派生视图。

**值得记录的修复史**（说明其质量门禁依赖"子代理可执行判据"）：

- narrative-writer 曾有三条规则空转：字数统计给了 Bash 命令但工具白名单没有 Bash、句长分布只能靠编、细纲逐项展开的最高优先明令没进 spawn 提示词——子代理只看见限制，按一个情节点一段平推成流水账。修复后首次落盘即进验收区间（对照组不到下限 73%）。
- **细纲照搬检测**：细纲把情节点写成成品散文句时正文只剩誊抄会被检出；配套「复沓锚句」字段让必须逐字进正文的原话（誓言、系统面板、案卷原话）不被误判。

### 2.6 状态层：文件系统记忆（其架构灵魂）

- **状态卡**：固定 7 栏、硬上限 12KB，续写只读这份文件，不靠对话记忆。
- **单一权威**：`_tracking-state.json` 由 `storyctl chapter commit` 写入 → 派生视图（上下文.md、伏笔.md、角色状态、时间线、逐章记录）全部重渲染。
- **手改派生文件会被 check 拒绝**——状态权威只能来自工具提交。
- **三层信息分离**：作者真相 ≠ 读者已知 ≠ 角色已知，防角色提前知道答案、伏笔写飞。
- **追踪检查点门**：v0.7.3 起四端补齐，防止静默写出没有追踪的正文（Claude Code 主力端曾缺这门）。

### 2.7 质量层：Hook + 确定性脚本

- **8 个 Hook**：会话管理、`guard-outline-before-prose`（无细纲拦截正文）、写后检查、追踪守卫（Bash 重定向写正文也拦）等。
- **写后自动检查**：`check-ai-patterns.js`（AI 句式）、`check-degeneration.js`（复读/退化）、标点与工程词规范化、字数目标、连贯性。
- **`story-deslop`**：本地 lint 式扫描（行号+命中片段+改写方向）；**blocking 只限确定性句式/标点问题**，其余 advisory 按读感判断；三遍去 AI 法 + 改写范例库 + 禁用词表；朱雀等外部 AI 检测只作自测参考。
- **`story-review`**：4 Agent 多视角审稿 + 番茄/起点/知乎评分标准。
- Stage 6 文风统计（Windows 兼容性曾修复）。

### 2.8 交付层

- `story-cover`：书名题材分析 + GPT-Image-2 出图（Codex 内置用量 / API 回退）。
- `story-import`：旧稿逆向重建为标准工程（大纲/设定/追踪），从下一章无缝续写；曾修复"把自己书误登记成对标"的 bug。

## 3. 关键工程机制清单（可借鉴点）

| 机制 | 实现 | 解决的问题 |
|------|------|-----------|
| 文件系统即数据库 | 一人一 md、卷纲/细纲两层、一章一文件、追踪目录管伏笔时间线 | 写到 200 章查 50 章伏笔不用翻正文 |
| 单一权威 + 只读派生 | `_tracking-state.json` → 派生视图，手改被拒 | 状态不被手滑污染 |
| 门禁前置 | outline-before-prose + 追踪检查点门 | 没细纲写不了正文，无追踪正文写不出来 |
| 上下文预算工程 | SKILL.md 瘦身 34%、按需读拆分、固定加载 −20~41% | 每会话 token 成本直接下降 |
| 子代理可执行判据 | 字数用 Bash 实测而非模型估算 | 质量门禁不空转 |
| 部署一致性 | `agents_version` 提示/降级 solo | 多端行为可预期 |
| 平台降级矩阵 | ZCode 无自定义 agent、OpenClaw 无 hook → 功能降级说明 | 能力声明诚实 |

## 4. 商业化分析

### 4.1 商业模式：本体免费，商业闭环在用户侧

- MIT 开源、零收费层——它是**流量与品牌入口**，不是收入产品。用户成本 = 宿主模型 API 费（需自带 key）。
- 真正的商业闭环发生在使用者一侧：作者用它产文 → 上架起点/番茄/知乎盐言 → 连载付费/短篇付费。
- 单人维护（worldwonderer），140+ commits 到 v0.6.11 后仍高频迭代（agents_version 25）——典型"一人公司"式开源项目。

### 4.2 商业化贴近度为什么高（四点）

1. **直接对齐付费节奏**：黄金三章、章尾钩子、爽点密度、付费卡点内置在方法论里，不是事后补。
2. **去 AI 味做成工程步骤**：lint 可检测、blocking/advisory 分级、三遍法+范例库，而不是祈祷模型不犯病。
3. **长篇一致性工程化**：文件系统记忆 + 三层信息分离 + commit 制状态，解决"写到 50 万字就崩"的核心痛点。
4. **方法论资产化**：拆文库是可复用模块资产，扫榜是选题输入——把"别人为什么火"变成自己的生产资料。

### 4.3 成本结构（用户视角）

- Opus/Sonnet/Haiku 分层：深度思考给贵模型，扫描给便宜模型——**用模型分层替代人工分层**。
- SKILL.md 瘦身与按需读直接降每会话固定成本（日更场景最敏感）。
- 无服务器、无订阅、无 GPU——边际成本 = token 费。

### 4.4 护城河与脆弱点

**护城河**（不在技术）：
- 方法论资产（拆文库结构、禁用词表、平台评分标准）；
- 六端 CLI 适配的覆盖面；
- 社区心智（★7.5k，"网文写作 skill"品类第一名片）。

**脆弱点**：
- 单人维护，bus factor = 1；
- 无收费层，无直接收入，长期投入靠热情；
- 强依赖宿主能力（降级矩阵：OpenClaw 无 hook 则门禁全失）；
- 状态层**无事务、无事件溯源**——文件直写，中断恢复靠文件冗余而非确定性重建（对比我方 store CAS + replay，纵深差一层）；
- 去味靠 lint 有天花板——社区实测"跑完仍有机械感"；
- 扫榜依赖页面抓取，平台改版/反爬即失效。

### 4.5 对我方双通道战略的启示

- **对方终点 = 交付文件**。连载发布、付费转化运营、有声书衍生全部不管——我方"网文平台连载付费 + 有声书付费"双通道终点恰是其空白地带。
- 对方证明了两件事：①方法论工程化有真实需求（★7.5k）；②"确定性门禁 + 文件记忆"路线被大规模验证可行。
- 我方应吸收：市场输入层（扫榜/拆文/R8 六项缺陷）、上下文预算工程、子代理可执行判据、平台评分标准对齐。
- 我方应坚持（纵深优势）：事务状态层（CAS + 快照 + replay）、尺号测量体系、revision 归因阶梯、双通道终点。

---

## 5. 结论

Oh Story 是"方法论工程化"的上限样板：架构选择（文件系统记忆 + 门禁前置 + 人机协同）与我方 Phase 0/1 内核同构但更浅——它赢在**市场输入侧完整**和**分发零摩擦**，弱在**状态层无事务纵深**、**去味无量化闭环**、**商业闭环只到交付**。

对我方的战略含义一句话：**R8 六项缺陷补的是它的长（市场输入），双通道终点打的是它的短（交付之后），内核纵深是我们的差异化壁垒。**
